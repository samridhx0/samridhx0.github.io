WHAT'S ACTUALLY INSIDE YOUR ELF BINARY (AND WHY MALWARE CARES)

Every executable on Linux is an ELF file. ELF stands for Executable and Linkable Format. It's a container format — it holds code, data, metadata, and the instructions the kernel and dynamic linker need to actually run the thing. Understanding it is prerequisite knowledge for binary exploitation, malware analysis, and making sense of tools like objdump, readelf, and nm.

The first four bytes of every ELF file are 7f 45 4c 46 — the ELF magic number. 45 4c 46 is ASCII for "ELF". Everything else follows from there.

The ELF header

readelf -h /bin/ls
ELF Header:
  Magic:   7f 45 4c 46 02 01 01 00 00 00 00 00 00 00 00 00
  Class:                             ELF64
  Data:                              2's complement, little endian
  Type:                              DYN (Position-Independent Executable file)
  Machine:                           Advanced Micro Devices X86-64
  Entry point address:               0x6aa0
  Start of program headers:          64 (bytes into file)
  Start of section headers:          136408 (bytes into file)
  Number of section headers:         30
  Section header string table index: 29

The important fields: Type (EXEC = fixed address, DYN = position-independent, meaning ASLR-compatible), Entry point (where execution begins — not main(), it's _start in the C runtime), and the offsets to program/section headers.

Sections vs segments

ELF has two views of the same binary: sections and segments. Sections are for linkers and debuggers. Segments (program headers) are for the kernel and dynamic linker at load time. They can overlap. 

# Sections (linker view)
readelf -S /bin/ls | head -30

# Segments (loader view)
readelf -l /bin/ls

Key sections:

  • .text — executable code. Read-only, executable.
  • .data — initialized global variables. Read-write, not executable.
  • .bss — uninitialized globals. Exists as metadata only (no disk space), zeroed at load time.
  • .rodata — read-only data: string literals, constants.
  • .got / .plt — Global Offset Table and Procedure Linkage Table: how dynamic linking works.
  • .dynamic — information for the dynamic linker.
  • .symtab / .dynsym — symbol tables (stripped in production binaries).

How dynamic linking works (and why GOT/PLT matters for exploits)

When your program calls printf(), it doesn't call the function directly. It calls a stub in the PLT (Procedure Linkage Table). The first time that stub is called, it triggers the dynamic linker to resolve the actual address of printf in libc and write it into the GOT (Global Offset Table). Subsequent calls go directly via the GOT entry. 

# See the PLT entries
objdump -d /bin/cat | grep -A3 '@plt'

# See what the GOT contains at runtime
# (with gdb)
gdb /bin/cat
(gdb) break main
(gdb) run
(gdb) info address printf    # where printf resolves to
(gdb) x/xg 0xGOT_ADDRESS    # what's in the GOT entry

Why this matters for security: the GOT is writable by default in older binaries. GOT overwrite attacks redirect function calls by writing a malicious address into a GOT entry. Modern mitigations like Full RELRO (-Wl,-z,relro,-z,now) make the GOT read-only after load time. Check whether a binary has it: 

checksec --file=/bin/ls
# or
readelf -l /bin/ls | grep GNU_RELRO

What strings and symbols tell you

# Extract printable strings from a binary
strings /path/to/suspicious_binary | grep -E 'http|curl|bash|/bin|/tmp|passwd|shadow'

# List exported/imported symbols
nm -D /path/to/binary 2>/dev/null
# U = undefined (imported), T = in .text (exported), W = weak symbol

# Check which shared libraries it needs
ldd /path/to/binary

Malware analysis starts here. Strings give you URLs, file paths, registry keys, suspicious function names. Symbol tables (if not stripped) tell you what the binary calls. ldd tells you its dependencies — a binary linked against libcrypto.so and nothing else is probably doing encryption and little else.

Checking binary hardening

# checksec is the standard tool
checksec --file=/bin/ls

# Output:
# RELRO:    Full RELRO       <- GOT is read-only after init
# STACK:    Canary found     <- stack smashing protection
# NX:       NX enabled       <- non-executable stack
# PIE:      PIE enabled      <- ASLR-compatible
# RPATH:    No RPATH         <- no hardcoded library path
# Symbols:  No Symbols       <- stripped

This is a quick audit of what exploit mitigations a binary has. A binary with no RELRO, no canary, no NX, and no PIE is a binary from the 1990s security model. You still find them on embedded systems and old enterprise software.

ELF injection: how malware infects binaries

Because ELF is a structured format, you can modify it programmatically. ELF infectors work by:

  1. Adding a new section (or extending an existing one) to hold shellcode.
  2. Changing the entry point to point at the shellcode.
  3. At the end of the shellcode, jumping to the original entry point.

The binary looks normal. file and checksec still report it as the original binary. It runs the original code after running yours. 

# Detect unusual section sizes or suspicious sections
readelf -S /bin/ls | awk '{print $2, $6}' | sort -k2 -rn

# Compare against a known-good copy
sha256sum /bin/ls
# Then compare with the package manager's expected hash:
dpkg --verify ls 2>/dev/null   # Debian/Ubuntu
rpm -V coreutils 2>/dev/null   # RHEL/Fedora

ELF is the container format for everything that runs natively on Linux. Reading it directly with readelf and objdump is a fundamental skill for malware analysis, binary exploitation, and hardening audits. Start with a binary you trust, learn what normal looks like, and anomalies become obvious.
