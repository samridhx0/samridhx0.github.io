WHY YOUR IPTABLES RULES DIE ON REBOOT (AND HOW TO FIX THAT FOREVER)

Every time your Linux box reboots, iptables starts clean. No rules. Your carefully constructed firewall from last week — gone. Your rate-limiting rules — gone. That DROP rule for the scanner that was hammering port 22 — gone.

This trips up a lot of people because everything seems fine right after you run iptables -L. The rules are there. They're working. Then the box reboots, and someone notices the firewall is wide open.

The kernel's netfilter module loads clean on boot. It doesn't save state anywhere by default. iptables rules live in kernel memory and have to be explicitly reloaded. Here's every way to handle this.

The basics: save and restore

# Save IPv4 rules to a file
iptables-save > /etc/iptables/rules.v4

# Save IPv6 rules
ip6tables-save > /etc/iptables/rules.v6

# Restore them
iptables-restore < /etc/iptables/rules.v4
ip6tables-restore < /etc/iptables/rules.v6

Make the directory first if it doesn't exist: mkdir -p /etc/iptables.

iptables-save dumps all tables (filter, nat, mangle, raw) and all chains in a format that iptables-restore can replay exactly. It's the lowest-level persistence approach and it works on every distro.

The problem: it doesn't run automatically on boot unless you wire it up. Here's how to do that.

The package way (Debian / Ubuntu)

apt install iptables-persistent netfilter-persistent

During install, the package asks if you want to save your current rules. Say yes. Afterward, netfilter-persistent installs a systemd service that runs iptables-restore at boot from /etc/iptables/rules.v4 and /etc/iptables/rules.v6.

When you update your rules later, save them explicitly:

# Either of these works:
netfilter-persistent save

# Or manually:
iptables-save > /etc/iptables/rules.v4

The systemd way (distro-agnostic)

No package required. Works anywhere with systemd:

mkdir -p /etc/iptables

# Save your current rules first
iptables-save > /etc/iptables/rules.v4
ip6tables-save > /etc/iptables/rules.v6

# Create the service unit
cat > /etc/systemd/system/iptables-restore.service <<'EOF'
[Unit]
Description=Restore iptables rules
Before=network-pre.target
Wants=network-pre.target

[Service]
Type=oneshot
ExecStart=/sbin/iptables-restore /etc/iptables/rules.v4
ExecStart=/sbin/ip6tables-restore /etc/iptables/rules.v6
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload
systemctl enable iptables-restore
systemctl start iptables-restore

The Before=network-pre.target ensures your firewall rules load before any network interfaces come up. This closes the window where the box is briefly unprotected at boot.

The modern way: nftables

nftables replaced iptables as the standard in Linux 3.13 (2014). It's the default on Debian 10+, RHEL 8+, Ubuntu 20.04+, Arch, and most current distros. The big difference from a persistence standpoint: nftables rules live in /etc/nftables.conf and a systemd service loads them at boot automatically. 

# Check if nftables is already set up on your system
systemctl status nftables
cat /etc/nftables.conf

A minimal nftables config that does what most people need:

#!/usr/sbin/nft -f

flush ruleset

table inet filter {
    chain input {
        type filter hook input priority 0; policy drop;

        # Allow established and related connections
        ct state established,related accept

        # Allow loopback
        iif lo accept

        # Allow SSH, HTTP, HTTPS
        tcp dport { 22, 80, 443 } accept

        # Allow ICMP
        icmp type echo-request accept
        icmpv6 type echo-request accept
    }

    chain forward {
        type filter hook forward priority 0; policy drop;
    }

    chain output {
        type filter hook output priority 0; policy accept;
    }
}
# Apply and enable
systemctl enable nftables
systemctl start nftables

# Test your rules without committing permanently
nft -f /etc/nftables.conf

# List current ruleset
nft list ruleset

nftables has unified IPv4/IPv6 handling with the inet family, so one rule covers both. The syntax is cleaner and the tool supports atomic rule replacement — you swap the entire ruleset in one operation, no window where you're half-applied.

The RHEL/Fedora/CentOS way: firewalld

# Add a service permanently
firewall-cmd --permanent --add-service=http
firewall-cmd --permanent --add-service=https

# Add a specific port
firewall-cmd --permanent --add-port=8080/tcp

# Apply without dropping existing connections
firewall-cmd --reload

# See what's currently allowed
firewall-cmd --list-all

--permanent writes to disk. Without it, changes are runtime-only and vanish on reboot. --reload applies the permanent rules without flushing existing connections. Firewalld manages zones, which lets you apply different rule sets to different network interfaces — useful on machines with a public interface and a private interface.

One critical gotcha with Docker

If you run Docker on the same machine as iptables, Docker injects its own iptables rules into the FORWARD chain and the nat table at startup. These rules are not in your saved ruleset. Every time Docker starts, it rewrites them.

This means your iptables-restore might overwrite Docker's rules, or Docker's rules might override yours, depending on timing. The interaction is messy. If you're running a Docker host, consider either using firewalld (which Docker has better support for) or accepting that Docker will manage those chains and only configure your INPUT rules manually. 

# See what Docker added to iptables
iptables -t nat -L -n
iptables -L DOCKER -n
iptables -L DOCKER-USER -n  # This chain is yours — Docker won't touch it

DOCKER-USER is a chain Docker creates specifically for user-defined rules. Rules you add here persist across Docker restarts. Use it.

Which approach to pick

  • New Debian 10+/Ubuntu 20.04+ install with no existing iptables rules: go with nftables directly
  • Existing iptables setup you're maintaining: iptables-persistent or the systemd unit, until you have time to migrate
  • RHEL/CentOS/Fedora: firewalld, it's the distro-native tool and well-supported
  • Docker host: use the DOCKER-USER chain for your rules regardless of the outer tool
