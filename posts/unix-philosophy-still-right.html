THE UNIX PHILOSOPHY IS STILL THE BEST SOFTWARE DESIGN DOC EVER WRITTEN

Doug McIlroy wrote it in 1978. Three rules:

Write programs that do one thing and do it well.

Write programs to work together.

Write programs to handle text streams, because that is a universal interface.

That's 46 years old. Predates the web. Predates personal computers as most people know them. Still a better framework for software design than most of what gets published today.

This isn't nostalgia. It's a claim about what makes software last and scale, backed by what's actually outlived what.

The pipe is the original microservices

# Find the top 20 IPs hitting your nginx API endpoints
cat /var/log/nginx/access.log \
  | grep "POST /api" \
  | awk '{print $1}' \
  | sort \
  | uniq -c \
  | sort -rn \
  | head -20

Six programs. No shared state. No API contracts. No shared libraries. No protobuf schema. They communicate through one interface: a stream of bytes on stdout/stdin. You can swap out any stage without touching the others. You can insert a new filter anywhere. You can replace awk with cut or a Python one-liner without breaking anything.

This is microservices. The Unix people built this pattern in the 1970s with text and file descriptors. The modern industry reinvented it with HTTP, containers, and service meshes — and somehow made it more complicated.

Everything is a file

# Read CPU temperature (Raspberry Pi / embedded Linux)
cat /sys/class/thermal/thermal_zone0/temp

# Write to a serial device
echo "AT+CMGF=1" > /dev/ttyUSB0

# Read from a webcam (frame capture)
ffmpeg -i /dev/video0 -frames:v 1 screenshot.png

# Open a TCP connection as a file descriptor
exec 3<>/dev/tcp/example.com/80
echo -e "GET / HTTP/1.0\r\nHost: example.com\r\n\r\n" >&3
cat <&3
exec 3>&-

Devices, hardware counters, kernel internal state, process information, sockets — all exposed as file paths. The same four operations — open, read, write, close — work for all of them. One abstraction, universally applicable.

You write shell scripts that manipulate sensor data, network connections, and process state using the exact same syntax. There's no "GPIO library" you need to learn. It's just a file.

Where Windows got it wrong

The Windows Registry is a hierarchical binary database that acts as the global configuration store for the entire OS, all applications, all hardware state, and all user preferences. It requires special tools to read (regedit, reg query). The format is opaque. When it breaks, the system often can't boot. You can't grep it, can't diff it, can't put it in a git repo.

Compare: on Linux, configuration lives in /etc/. Text files. Every tool ever written can read them. You grep them, diff them, version-control them, copy them to a new machine with scp, template them with Ansible, validate them with standard parsers. The configuration format for nginx is different from the one for sshd which is different from the one for cron, and that's fine — because they're all just text files your existing tools can handle.

DLL Hell was the Windows manifestation of the opposite of "do one thing." Shared libraries in a flat namespace, fighting over versions, no stable ABI guarantees, application installers that would overwrite system DLLs to get the version they needed. The Unix approach of package managers, versioned shared library names (libfoo.so.2), and static linking as an escape hatch handled this better.

The composability test

A useful test for any system: can you compose it with things that don't know about it?

# These tools don't know about each other, but compose trivially:
ps aux | awk '{print $1}' | sort | uniq -c | sort -rn
# "which users have the most processes running right now"

# This works because ps writes to stdout, awk reads from stdin
# They share one interface: text

Contrast with a system designed as a monolith: to get user process counts, you'd open a management console, navigate to a metrics section, filter by user, export to CSV, open in Excel. The data is trapped inside the system's interface. It doesn't compose.

The rule that aged worst: text streams

McIlroy's third rule — text as the universal interface — is the one that aged most visibly. Protocol Buffers, MessagePack, and Apache Avro are more precise than newline-delimited text for structured data. A grep over protobuf output is not how you query it.

But the rule was never about text specifically. It was about having a universal interface at all — something everything can produce and consume without negotiation. In 1978, text was the only practical universal interface. Today you'd argue for JSON or binary protocols. The principle holds; the implementation detail (text) doesn't need to.

Why it still matters

The systems that aged well — Git, nginx, PostgreSQL, SQLite — all have clear scope and clean interfaces. Git doesn't manage your CI/CD pipeline. nginx doesn't manage your certificates (well, the modern additions do, but the core doesn't). PostgreSQL doesn't tell your application how to query it beyond SQL.

The systems that didn't age well — early enterprise Java middleware, COM objects, DCOM, CORBA — tried to be everything and define all interfaces. They accreted complexity in proportion to the number of problems they tried to solve.

"Do one thing and do it well" is boring to say and hard to enforce. Every project eventually encounters a feature request that seems adjacent enough to justify expanding scope. The ones that hold the line outlast the ones that don't.

The philosophy isn't Unix-specific. It's a set of constraints that produce durable software. That's why it's still worth reading.
