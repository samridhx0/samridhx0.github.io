PTRACE: THE SYSCALL THAT RUNS YOUR DEBUGGER AND YOUR ROOTKIT

ptrace is syscall 101 on x86_64 Linux. It gives one process — the tracer — direct access to another process's memory, registers, and system call stream. This is how gdb works. It's how strace works. It's also how a chunk of Linux process injection works.

Understanding ptrace is understanding a major attack surface. The same mechanism that lets you debug your code lets someone inject code into your running processes.

What ptrace actually does

The API is a single syscall with a request enum and a target PID:

#include <sys/ptrace.h>
#include <sys/wait.h>

// Attach to a running process
ptrace(PTRACE_ATTACH, pid, NULL, NULL);
waitpid(pid, NULL, 0);  // wait for the SIGSTOP delivery

// Read a word from the tracee's address space
long word = ptrace(PTRACE_PEEKDATA, pid, (void*)addr, NULL);

// Write arbitrary bytes to the tracee's address space
ptrace(PTRACE_POKEDATA, pid, (void*)addr, (void*)new_word);

// Read the tracee's registers
struct user_regs_struct regs;
ptrace(PTRACE_GETREGS, pid, NULL, ®s);

// Modify registers (e.g. change RIP to point at injected shellcode)
regs.rip = (unsigned long long)target_addr;
ptrace(PTRACE_SETREGS, pid, NULL, ®s);

// Resume execution
ptrace(PTRACE_CONT, pid, NULL, NULL);

That PTRACE_POKEDATA call writes arbitrary bytes to any address in the tracee's address space. Combined with PTRACE_SETREGS to redirect execution, you have process injection. No kernel exploit required. Just ptrace.

The injection recipe

Classic Linux process injection with ptrace looks like this:

  1. Find a target process (something that runs as root, or something that has network access you want to abuse).
  2. Call PTRACE_ATTACH. The target gets SIGSTOP and freezes.
  3. Find a writable region in /proc/PID/maps — or use ptrace to call mmap() in the target to allocate new memory.
  4. Write your shellcode with PTRACE_POKEDATA in word-sized chunks.
  5. Save the original registers, set RIP to your shellcode, call PTRACE_CONT.
  6. Wait for it to finish, restore original registers, detach.

The process in ps still shows the original name. The memory map will have an anonymous executable region if you mmap'd new space, but that's the only obvious artifact.

strace is just ptrace with extra formatting

# Attach to a running nginx worker
strace -p $(pgrep nginx | tail -1)

# Trace with full argument strings
strace -s 256 -p PID

# Count syscalls (useful for performance work)
strace -c -f ./mybinary

strace uses PTRACE_SYSCALL to stop the tracee at every syscall entry and exit, log the arguments, then resume. The overhead is real — a heavily traced process can slow down by 10-50x. Don't run strace on a production database and wonder why latency spiked.

Detecting whether a process is being traced

grep TracerPid /proc/TARGET_PID/status
# TracerPid: 0      <- nothing attached
# TracerPid: 2341   <- PID 2341 is tracing this process

Malware and CTF binaries use this to detect analysis: 

// Anti-debug: PTRACE_TRACEME fails if already being traced
if (ptrace(PTRACE_TRACEME, 0, 0, 0) == -1) {
    // Someone attached before us, bail out
    _exit(1);
}

This is a one-liner to bypass in gdb: catch syscall ptrace then set a return value override.

YAMA ptrace_scope: the kernel-level restriction

cat /proc/sys/kernel/yama/ptrace_scope
  • 0 — Any process can trace any other process with the same UID
  • 1 — A process can only trace its own children (default on Ubuntu/Debian)
  • 2 — Only processes with CAP_SYS_PTRACE can trace
  • 3 — ptrace is completely disabled, no exceptions

Most desktop Linux distros ship with scope=1. This blocks the cross-process injection technique above unless you're running as root. Corporate hardened images often set scope=2 or 3. 

# Temporarily loosen (requires root)
echo 0 > /proc/sys/kernel/yama/ptrace_scope

# Persist across reboots
echo "kernel.yama.ptrace_scope = 1" >> /etc/sysctl.d/10-ptrace.conf

seccomp can kill ptrace entirely

If a process drops the ptrace syscall from its seccomp whitelist, it can't be used as a tracer, and it can't be made into a tracee either (well, it can be attached to, but it can't call ptrace itself). Docker's default seccomp profile blocks ptrace — which is why you can't run strace inside a stock Docker container without --cap-add SYS_PTRACE or a custom seccomp profile. 

# This fails in a default Docker container
docker run ubuntu strace ls
# strace: ptrace(PTRACE_TRACEME, ...): Operation not permitted

# This works
docker run --cap-add SYS_PTRACE ubuntu strace ls

One practical defensive use

If you're writing a sandboxed process that runs untrusted code, you can use ptrace to intercept and filter syscalls from the child — essentially building a syscall policy enforcer in userspace. This is how some browser sandboxes worked before seccomp-bpf became standard. It's slower than seccomp and requires a dedicated tracer process, but it's more flexible for dynamic policy decisions.

Understanding ptrace is a prerequisite for understanding debuggers, sandboxes, malware injection, and container security. It's one of those syscalls that quietly touches everything.
