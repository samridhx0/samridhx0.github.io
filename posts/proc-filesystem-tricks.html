YOUR /PROC IS A GOLDMINE. YOU JUST DON'T KNOW IT YET.

/proc is not a real filesystem. Nothing in it lives on disk. It's a window the kernel synthesizes on-demand every time you open a file there. Read /proc/meminfo and the kernel generates that output in real time from its internal memory accounting structures. There's no inode, no sectors, no persistence.

Most people know /proc/cpuinfo and maybe /proc/meminfo. The per-process directories under /proc/PID/ are where it gets interesting, and where most sysadmins leave a lot on the table.

Reading a process's memory layout

cat /proc/$(pgrep firefox)/maps

Output looks like this:

7f4a2c000000-7f4a2c021000 r--p 00000000 fd:01 1234567 /usr/lib/x86_64-linux-gnu/libc.so.6
7f4a2c021000-7f4a2c179000 r-xp 00021000 fd:01 1234567 /usr/lib/x86_64-linux-gnu/libc.so.6
7f4ab0000000-7f4ab0800000 rw-p 00000000 00:00 0

Each line is an address range, permissions, file offset, device, inode, and path. The p in permissions means private (copy-on-write). An s means shared. Anonymous mappings have no path — those are heap regions, stack, and raw mmap'd memory. If you see a writable+executable anonymous region, that's worth looking at.

Open file descriptors

ls -la /proc/$(pgrep sshd | head -1)/fd

Every open file, socket, pipe, and device node shows up here as a symlink. Sockets appear as socket:[inode]. Cross-reference those inodes with /proc/net/tcp to get the actual connection details. This is how tools like lsof work — they just automate what you can do manually right here.

One particularly useful pattern: if a process has a file open that's been deleted from the filesystem, it shows up here as /path/to/file (deleted). That's not an accident — that's a running process that erased its own binary. Malware does this routinely.

Environment variables at runtime

cat /proc/1234/environ | tr '\0' '\n'

Environment variables in /proc are null-byte separated. The tr '\0' '\n' makes it human-readable. This is useful when you want to see what secrets got passed into a running process — AWS credentials, API tokens, database passwords. If a process inherited them from its parent, they'll be here.

Note: reading another process's environ requires either being root or having the same UID.

Network connections without netstat

cat /proc/net/tcp

The output is in hex, little-endian. Column two is the local address and column three is the remote address, formatted as XXXXXXXX:PPPP where the first part is the IP and the second is the port.

Decode it manually:

awk 'NR>1 {print $2, $3, $4}' /proc/net/tcp | while read local remote state; do
  python3 -c "
import socket, struct
def decode(h):
    ip, port = h.split(':')
    ip = socket.inet_ntoa(struct.pack('', decode('$remote'), 'state=$state')
" 2>/dev/null
done

State 0A means LISTEN. 01 is ESTABLISHED. This is exactly what ss and netstat read under the hood.

Detecting if a process is being traced

grep TracerPid /proc/$$/status

If TracerPid is non-zero, something is attached to that process with ptrace — a debugger, strace, or something less legitimate. This is how CTF challenges implement anti-debug checks, and it's also how you can quickly check whether a suspicious process on a production box is being monitored. 

# Check a specific PID
grep TracerPid /proc/1337/status
# TracerPid: 0      <- not being traced
# TracerPid: 4567   <- PID 4567 is attached

Kernel parameters you can flip live

# Let non-root users read dmesg
echo 0 > /proc/sys/kernel/dmesg_restrict

# Disable ASLR temporarily (useful for debugging)
echo 0 > /proc/sys/kernel/randomize_va_space

# Check how many file handles are open vs the system max
cat /proc/sys/fs/file-nr

These changes are not persistent — they vanish on reboot. For persistence, use sysctl.conf or drop a file in /etc/sysctl.d/.

Finding deleted-but-running processes

ls -la /proc/*/exe 2>/dev/null | grep deleted

The /proc/PID/exe symlink points to the binary that launched the process. If the binary was deleted after launch, the symlink still exists but the path shows (deleted). This is one of the faster ways to spot self-deleting malware without pulling in a full forensics toolkit.

One more: namespace inspection

# See what namespaces a process is in
ls -la /proc/$(pgrep dockerd | head -1)/ns/

Each symlink in /proc/PID/ns/ represents a namespace (network, mount, pid, uts, ipc, user). Two processes that share the same inode number for a given namespace are in the same namespace. This is useful when debugging container escapes or just understanding what's isolated from what.

/proc is already on your system. It doesn't need installing. Next time you reach for a monitoring tool, check if the answer is already sitting in a file under /proc first.
