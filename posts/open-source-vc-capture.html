OPEN SOURCE IS EATING ITSELF: THE VC CAPTURE PROBLEM

The original open source promise was radical: software that legally belonged to everyone. The GPL said if you distribute software, you distribute freedoms. The BSD crowd said do whatever you want. Linus Torvalds built a kernel and let the world modify it. For a while, this worked.

It's still working for some things. The Linux kernel is fine. PostgreSQL is fine. SQLite is fine. These projects have stable governance, corporate contributors who don't control the codebase, and communities that would fork overnight if someone tried to pull a fast one.

But a pattern has emerged with VC-backed "open source" companies that should make you skeptical every time you bet your infrastructure on a project with a commercial backer.

The pattern

It goes like this:

  1. Release the software under a permissive license (Apache 2.0, BSD, MIT).
  2. Build a community. Get developers to adopt it, contribute to it, write documentation, give talks at conferences.
  3. Raise venture capital. Now you have payroll to meet and investors expecting returns.
  4. Watch AWS/Azure/GCP offer your product as a managed service, monetizing your community's work without meaningfully contributing back.
  5. Relicense to something that blocks cloud providers from competing.

This is not a hypothetical. It has happened repeatedly.

The cases

MONGODB — 2018

MongoDB switched from AGPL to the Server Side Public License (SSPL). The SSPL's key clause: if you offer MongoDB as a service, you must open-source the entire software stack used to provide that service — including your orchestration, monitoring, backups, everything. Designed specifically to be impossible for AWS to comply with. Result: MongoDB Inc. controls a database used by hundreds of thousands of developers who chose it under an open source license. Debian and Red Hat removed it from their package repos because SSPL is not considered open source by OSI.

ELASTICSEARCH — 2021

Elastic switched Elasticsearch and Kibana from Apache 2.0 to dual-license: Elastic License 2.0 and SSPL. The explicit reason stated by Elastic's CEO: Amazon was running "Amazon Elasticsearch Service" without contributing meaningfully. Amazon's response: fork it. They forked both Elasticsearch and Kibana into OpenSearch, kept it Apache 2.0, and most major cloud providers followed. Elastic lost control of the upstream narrative.

HASHICORP / TERRAFORM — 2023

HashiCorp switched Terraform from Mozilla Public License 2.0 to the Business Source License (BSL 1.1) in August 2023. BSL allows use but prohibits "competitive" use — specifically, you can't use BSL Terraform to build a product that competes with HashiCorp's commercial offerings. The community forked Terraform into OpenTofu within weeks. OpenTofu is now under the Linux Foundation. IBM acquired HashiCorp in 2024 for $6.4 billion.

REDIS — 2024

Redis Ltd. switched Redis from BSD to dual-license RSALv2 and SSPL. AWS had been running ElastiCache (Redis-compatible) at scale. The community response was immediate: the major cloud providers — AWS, Google, Oracle — forked Redis into Valkey under the Linux Foundation. Valkey is now BSD licensed. Redis lost the single most important asset it had: being the canonical in-memory data store everyone defaults to.

What SSPL and BSL actually are

Neither SSPL nor BSL is approved by the Open Source Initiative as an open source license. OSI's definition requires that the license not restrict fields of endeavor — you can't restrict commercial use, you can't restrict who runs it, you can't restrict what other software it gets bundled with.

SSPL and BSL both restrict specific use cases (competing services, combining with certain other software). They're source-available licenses — you can read the code, maybe modify it for internal use — but they're not open source in the traditional sense.

Calling them "open source" is marketing. Technically inaccurate marketing that confuses enterprises into thinking they're betting on something community-governed.

The counter-moves

The AGPL (GNU Affero General Public License) addresses the "software as a service" loophole that AWS exploits. AGPL requires that if you run modified AGPL software over a network, you must provide source to users of the service. Nextcloud, Mastodon, GitLab's core, and many other projects use it. AWS generally won't touch AGPL software, which is either a feature or a bug depending on your perspective.

The Functional Source License (FSL) is a newer approach: full commercial restrictions during the first two years, then the software becomes Apache 2.0 automatically. You get a runway to monetize before competitors can build managed services, but the community retains a guaranteed open source future.

Developer cooperatives: Gitea moved to a cooperative structure in 2022, where the commercial entity (Gitea Ltd.) is majority-owned by its contributors. No single corporate backer can unilaterally relicense.

What this means for your infrastructure choices

When evaluating open source infrastructure software, the license is only one dimension. Ask:

  • Who owns the trademark? (Controls the brand even if the code is forked)
  • Who controls the primary repository?
  • What's the Contributor License Agreement — does it require copyright assignment to the company?
  • Who's funding this, and what's their exit strategy?
  • Is there a foundation (Apache, Linux Foundation, CNCF) or just a company with open code?

Projects where contributors sign CLAs assigning copyright to the company are one board vote away from relicensing. Projects under neutral foundations with distributed copyright are much harder to capture.

The technical quality and the governance structure are independent variables. A project can be technically excellent and still be a governance timebomb. Check both.
