CONTAINERS ARE JUST LINUX NAMESPACES. HERE'S THE PROOF.

Every time someone explains containers, they use a Docker command as the first example. That's the wrong starting point. Docker is a tool that automates container creation. The actual mechanism is Linux namespaces and cgroups — kernel features that have been around since 2002 and 2006 respectively.

You can create a functional container with a single command and no Docker installed. Here's how.

What namespaces are

A Linux namespace wraps a global resource and provides a process with an isolated view of it. Processes inside a namespace think they have the entire resource to themselves. From outside, you can see everything.

There are 8 namespace types:

  • mnt — mount points (each process sees a different filesystem tree)
  • pid — process IDs (PID 1 inside looks like PID 1, but it's some other PID on the host)
  • net — network interfaces, routing tables, firewall rules
  • ipc — System V IPC and POSIX message queues
  • uts — hostname and NIS domain name
  • user — user and group IDs (UID 0 inside maps to an unprivileged UID outside)
  • cgroup — cgroup root (added in 4.6)
  • time — system clock offsets per-namespace (added in 5.6)

Build a container by hand

# Install debootstrap if needed
apt install debootstrap

# Create a minimal Debian root filesystem
mkdir /tmp/mycontainer
debootstrap --variant=minbase bookworm /tmp/mycontainer http://deb.debian.org/debian

# Now launch a process with isolated namespaces
unshare --mount --uts --ipc --net --pid --fork --user \
    --map-root-user \
    chroot /tmp/mycontainer /bin/bash

That's a container. No Docker. No containerd. Just unshare (a utility that calls the unshare(2) syscall) and chroot (which changes the root directory for a process).

The --user --map-root-user flags create a user namespace where your current unprivileged user maps to UID 0 inside. This is how rootless containers work.

Inspect namespaces with nsenter

# See what namespaces a running process is in
ls -la /proc/$(pgrep containerd | head -1)/ns/

# Output:
# lrwxrwxrwx ... cgroup -> cgroup:[4026531835]
# lrwxrwxrwx ... ipc -> ipc:[4026531839]
# lrwxrwxrwx ... mnt -> mnt:[4026531840]
# lrwxrwxrwx ... net -> net:[4026531992]
# lrwxrwxrwx ... pid -> pid:[4026531836]
# ...

# Enter a running container's namespaces
# (equivalent to docker exec, but without Docker)
nsenter --target PID_OF_CONTAINER_INIT --mount --pid --net --uts -- /bin/bash

Two processes share a namespace if and only if their namespace symlinks point to the same inode. That's it. That's the whole mechanism.

Network namespace in isolation

# Create a named network namespace
ip netns add myns

# Run a command inside it
ip netns exec myns ip addr show
# Only shows lo — completely isolated from host networking

# Create a veth pair (virtual ethernet cable between namespaces)
ip link add veth0 type veth peer name veth1

# Move one end into the namespace
ip link set veth1 netns myns

# Configure both ends
ip addr add 10.0.0.1/24 dev veth0
ip link set veth0 up

ip netns exec myns ip addr add 10.0.0.2/24 dev veth1
ip netns exec myns ip link set veth1 up
ip netns exec myns ip link set lo up

# Now ping from the namespace to the host
ip netns exec myns ping 10.0.0.1

This is exactly what Docker does when it creates a bridge network. The docker0 bridge interface on your host, the veth pairs that appear in ip link show with names like veth3a5b1c2 — all of this is the same mechanism, automated.

cgroups: the resource limits half

Namespaces handle isolation (what a process can see). cgroups handle resource limits (how much a process can use). Together they make containers. 

# Create a cgroup (v2 syntax, modern systems)
mkdir /sys/fs/cgroup/mygroup

# Limit memory to 256MB
echo "268435456" > /sys/fs/cgroup/mygroup/memory.max

# Limit CPU to 50% of one core
echo "50000 100000" > /sys/fs/cgroup/mygroup/cpu.max

# Add a process to the cgroup
echo $$ > /sys/fs/cgroup/mygroup/cgroup.procs

# Now run something memory-hungry and watch it get killed
python3 -c "x = bytearray(1024*1024*512)"
# Killed

The container escape angle

Namespaces are only as strong as their configuration. Common weaknesses:

  • No user namespace: if the container runs as real UID 0 (root on the host), any container escape gives you host root. Rootless containers with user namespaces isolate this.
  • Privileged containers: docker run --privileged disables most namespace isolation. The container can mount the host filesystem, load kernel modules, and manipulate host networking. This is a full security boundary bypass by design.
  • Shared PID namespace: docker run --pid=host shares the host's PID namespace. The container can see all host processes and ptrace them (if YAMA ptrace_scope allows).
  • Mounted Docker socket: -v /var/run/docker.sock:/var/run/docker.sock inside a container gives it full control over the Docker daemon, which runs as root. Classic container escape that doesn't require any kernel exploit. 
# Check if you're in a container
cat /proc/1/cgroup | grep docker
ls /.dockerenv 2>/dev/null
grep -q "container=lxc" /proc/1/environ 2>/dev/null && echo "lxc container"

Containers are powerful and well-understood. Most container security incidents aren't kernel exploits — they're misconfiguration. Know the primitives and you know what the misconfigurations are exposing.
