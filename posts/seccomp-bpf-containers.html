SECCOMP-BPF: THE SYSCALL FILTER YOUR CONTAINERS ACTUALLY NEED

seccomp shipped in Linux 2.6.12 in 2005. The original mode was savage: a process could only call read(), write(), exit(), and sigreturn(). Anything else triggered SIGKILL. No exceptions. Useful for running untrusted binary blobs in an extremely narrow box, basically unusable for anything real.

seccomp-bpf landed in 3.5 in 2012 and changed everything. Instead of the binary allow/kill mode, you write a BPF (Berkeley Packet Filter) program that inspects each syscall number and arguments, then returns a disposition: ALLOW, ERRNO, KILL, TRAP, or TRACE.

That flexibility made seccomp practical. Today it's used by Chrome's renderer sandbox, Docker's default container profile, Kubernetes pods, and Android apps running on the zygote process.

What Docker blocks by default

Docker's default seccomp profile blocks around 44 syscalls. Some notable ones:

  • ptrace — blocks debugger attachment and process injection
  • keyctl, add_key, request_key — kernel keyring access
  • perf_event_open — hardware performance counters (used in some side-channel attacks)
  • reboot, kexec_load — obvious
  • mount, umount2 — filesystem mounting
  • syslog — kernel log
  • clock_settime — setting system time
  • pivot_root — changing root filesystem
# Run without any seccomp filtering (for comparison / debugging)
docker run --security-opt seccomp=unconfined ubuntu bash

# Try something that the default profile blocks
docker run ubuntu strace ls
# strace: ptrace(PTRACE_TRACEME, ...): Operation not permitted

Finding your process's actual syscall set

Before writing a profile, you need to know what syscalls your application actually makes. strace -c is the fastest way:

# Run with syscall counting
strace -c -f ./mybinary 2>&1

# Output looks like:
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 41.23    0.000841          14        60           read
 28.91    0.000590           7        82           write
 12.44    0.000254           6        43           openat
...
------ ----------- ----------- --------- --------- ----------------
100.00    0.002040                   312        18 total

Take that list, filter out the error-only ones that are expected, and you have your allow-list.

Writing a minimal seccomp profile

Docker's seccomp profiles are JSON. The format is an OCI spec extension:

{
  "defaultAction": "SCMP_ACT_ERRNO",
  "architectures": ["SCMP_ARCH_X86_64", "SCMP_ARCH_X86", "SCMP_ARCH_X32"],
  "syscalls": [
    {
      "names": [
        "read", "write", "open", "close", "stat", "fstat", "lstat",
        "mmap", "mprotect", "munmap", "brk", "exit_group", "futex",
        "set_tid_address", "set_robust_list", "rt_sigaction",
        "rt_sigprocmask", "arch_prctl", "pread64", "access",
        "execve", "openat", "getdents64", "newfstatat", "ioctl",
        "getpid", "gettid", "clock_gettime", "nanosleep"
      ],
      "action": "SCMP_ACT_ALLOW"
    }
  ]
}
# Apply it
docker run --security-opt seccomp=/path/to/profile.json myimage

defaultAction: SCMP_ACT_ERRNO means any syscall NOT in the allow-list returns EPERM instead of killing the process. This is more debuggable than SCMP_ACT_KILL — you'll see the permission error in logs rather than a sudden crash.

In Kubernetes

apiVersion: v1
kind: Pod
metadata:
  name: myapp
spec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault   # Docker/containerd's default profile
  containers:
  - name: myapp
    image: myapp:latest
    securityContext:
      allowPrivilegeEscalation: false
      runAsNonRoot: true

RuntimeDefault applies the container runtime's default seccomp profile. Before Kubernetes 1.27, the default was Unconfined — no filtering at all. If you're running older clusters, this is something to audit.

For a custom profile, put the JSON file on the node at a path under /var/lib/kubelet/seccomp/ and reference it with type: Localhost.

Bypasses worth knowing

seccomp-bpf is strong but not magic:

  • 32-bit syscall confusion: On x86_64, if a process can switch to 32-bit mode (via a far call or crafted int 0x80), it uses 32-bit syscall numbers which are different from 64-bit ones. A profile that only adds SCMP_ARCH_X86_64 architecture may not cover 32-bit syscalls.
  • Argument TOCTOU: seccomp inspects syscall arguments at the BPF evaluation point, but pointer arguments point into process memory. For some syscalls, a racing write to that memory could change the argument after the BPF check but before the kernel processes it. Limited practical impact but worth knowing for advanced policy writing.
  • Allowed-but-abusable syscalls: memfd_create creates an anonymous memory-backed file descriptor. Combined with fexecve, you can run a binary entirely in memory without touching the filesystem. This uses only allowed syscalls in most profiles. Legitimate use case for runtime loaders, illegitimate use case for fileless malware. 
# Detect memfd-based execution in a running system
ls -la /proc/*/exe 2>/dev/null | grep memfd
# or
ls -la /proc/*/fd/* 2>/dev/null | grep memfd

The audit workflow

# 1. Profile the application's syscall set
strace -c -f -o /tmp/syscalls.txt ./myapp

# 2. Build a minimal JSON profile from the output
# (manual for now, tools like oci-seccomp-bpf-hook automate this)

# 3. Test with SCMP_ACT_LOG instead of KILL to see violations in syslog
# (requires kernel 4.14+)

# 4. Check violations
journalctl -k | grep seccomp

The default Docker profile is a reasonable baseline. For production workloads where you know the exact syscall set, a custom minimal profile significantly reduces the kernel attack surface exposed to a compromised container.
